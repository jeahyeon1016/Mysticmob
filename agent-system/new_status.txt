MythicMobs — 프로젝트 현재 상태
읽는 조건: 프로젝트 연결·이전·전체 현황 확인·작업 재개 때. 개별 몹의 단순 수정에는 해당 몹 문서와 코드만 읽는다.
기록 기준
본 문서는 현재 로컬 파일·서버 로그·원격 main을 대조한 상태다. 기준 커밋 0257788d049d6f200d12c65d3fcd2945cc961660 (fix(silbar): restore poison slime walk attacks and sync instructions). 인게임 정상 완료를 뜻하지 않는다.
연결
실제 Git 루트: D:\ai agent\projects\mythicmobs
브랜치 main, origin: https://github.com/jeahyeon1016/rpg.git
로컬 HEAD와 실제 원격 main은 위 커밋으로 일치한다. 포이즌 슬라임 walk 복구, 최신화 요청 지침, Gemini용 Docs 연결 안내를 커밋·push했고 작업 트리는 깨끗하다.
agent.json의 local_path와 github_remote가 실제 Git 연결과 일치한다. D: 프로젝트 이전은 완료됐으며 신규 저장소 생성이나 C: 경로 재탐색은 필요 없다.
구현 현황
원본 구조는 model/지역/몹 이름/ (*.bbmodel, *_몹.yml, *_스킬.yml). 오크킹은 사용자 판단으로 개발 완료; 모션·글레이브 전환 끊김은 보류 버그이며 외형 소실은 보고되지 않았다. 소환 궁수 수정의 인게임 개선 여부는 미확인. 기존 Mobs/OrcKing, Mobs/Orc_Archer 계약을 유지한다.
포이즌 슬라임: 구현 파일은 있으나 외형 소실 미해결로 완료 판정 보류. 베이스는 ZOMBIE, 모델 ID는 rpg_poison_slime_cube. 정상 사양은 walk의 0.75초 착지마다 50% 확률을 한 번 판정하고, 반경 15블록 내 가까운 플레이어 최대 3명에게 각각 점액 1발(피해 4, 중력 0.25, 독 I 100틱)을 발사하는 것이다. 한 명이면 한 발이다. idle 분리 진단을 종료하고 type=walk;state=walk로 복구했다. model/ 원본과 서버 적용 사본이 일치하며 walk·착지 발사 연결의 정적 검사를 통과했다. 복구 후 리로드·새 개체의 인게임 패턴 확인은 남아 있다. 상세 문서는 Mobs/PoisonSlime의 “PoisonSlime — 포이즌 슬라임”이다.
지역 준비 파일: 실바르의 마법 슬라임·엔트 계열·천년목, 바르칸의 자이언트 오크·카시우스, 에르덴의 고블린 정찰병 등이 원격 커밋에 포함됐다. 파일 존재는 구현·인게임 검증 완료를 뜻하지 않는다.
환경·검증
실제 서버 로그에서 Paper 26.1.2, MythicMobs 5.13.0, ModelEngine 4.1.0, BetterModel 3.4.1 로딩을 확인했다. Fabled 1.0.4-R0.98-SNAPSHOT도 설치돼 있다. 포이즌 슬라임의 원본과 서버 mobs/skills/blueprints 사본을 반영했고 정적 참조·키프레임·대상 제한·사본 해시 검사를 통과했다. 이 검사는 외형 소실 해결을 입증하지 않는다.
기존 오크킹·궁수의 정적 검사 통과 기록은 과거 검증이며 이번 작업에서 재실행하지 않았다. 이전 분리 진단에서는 포이즌 슬라임을 리로드 후 새 개체로 테스트했고 전체 또는 판 모양 일부만 남는 소실이 계속 관찰됐다. enable-rcon=false로 리로드·인게임 조작은 사용자가 수행했다.
남은 작업과 제약
미해결 버그 — 포이즌 슬라임 외형 소실: 규칙성이 확인되지 않았고 전체가 사라지거나 판 모양 일부만 남았다. 외형이 사라져도 공격하던 사례가 있다. /meg resync와 culling OFF 테스트에서도 재현됐으며 culling 임시 설정은 원복했다. idle-only 분리 테스트에서도 재현됐다. 원인은 미확정이며 추가 조사는 보류한다.
다음 조사 시 정상 작동하던 기존 몹과 Codex 작업 파일의 모델 적용 옵션·애니메이션 연결·bbmodel 차이를 먼저 비교한다. 사용자는 새로 작업한 몹들에서 문제가 발생했다고 보고했다. 클라이언트 모드 충돌이나 ModelEngine 자체 결함은 확정되지 않았고 순정 클라이언트 비교는 미실시다. 현재 파일은 walk 정상 사양으로 복구했으며, 외형 소실 수정 완료로 간주하지 않는다.
Gemini Docs 연결은 D:\ai agent\agent-system\gdocs.cmd의 일반 Docs API로 구성했다. 최초 OAuth 인증과 중앙 문서 읽기, 본문 변경 없는 0건 치환으로 쓰기 API 권한을 검증했다. 이후 인증은 자동 갱신한다. Preview 등록이 필요한 docs MCP 대신 이 도구를 사용한다. 실제 최신화 후 읽기 검증이 있어야 완료로 판단한다. 규칙·현재 상태·몹 문서의 갱신 시점과 Git 업로드는 사용자 요청 범위를 따른다.
AI 인계 시작 절차
새 AI/새 세션에서 작업을 이어갈 때는 이 문서를 중앙 상태 진입점으로 사용한다.
1. 이 문서를 먼저 읽고 프로젝트의 현재 연결·구현 현황·미확정 사항을 파악한다.
2. 이후 현재 사용자 요청과 직접 관련된 몹/작업 문서만 추가로 읽는다. 전체 문서를 선제적으로 읽지 않는다.
3. 로컬 프로젝트에서는 AGENTS.md와 현재 작업에 필요한 실제 소스만 확인한다.
4. 문서에 기록된 설계·상태와 로컬 코드가 다르면 어느 한쪽을 임의로 정답 처리하지 말고 차이를 보고한다. 현재 구현 확인에는 실제 코드·실행 상태를, 의도된 동작 확인에는 최신 사용자 요구와 확정 명세를 사용한다.
5. 원격 Git 상태와 로컬 상태를 구분한다. 미추적·미커밋 파일은 다른 PC의 clone에 존재하지 않을 수 있으므로 작업 시작 시 git status를 확인한다.
6. 이전 AI의 완료 보고만 믿지 말고 필요한 경우 diff·직접 참조·검증 결과를 확인한다.
7. 인계 목적만으로 별도 ROADMAP·SPRINT·DECISION_LOG 문서를 자동 생성하지 않는다. 현재 상태 문서와 관련 작업 문서로 충분하면 그대로 이어간다.
Antigravity/Gemini 인계 테스트 기준
- 중앙 상태 문서를 실제로 읽었는가
- 현재 요청과 관련된 문서만 골라 읽는가
- 로컬 Git 상태를 별도로 확인하는가
- 문서와 코드의 불일치를 발견했을 때 임의 수정하지 않고 보고하는가
