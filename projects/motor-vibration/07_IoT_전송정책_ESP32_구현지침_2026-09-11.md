# IoT 전송정책 변경 — ESP32 구현 지침

- 작성일: 2026-09-11
- 기준 제안서: `IoT_전송정책_개발제안서_20260910.md`
- 대상 저장소: `D:\github\MotorDiagnosis`
- 대상 장치: ESP32-S3 N8, ADXL345, INMP441
- 목표 정책: 평상시 5분 묶음 전송 + 이상 징후 우선 전송

## 0. 이 문서의 사용 원칙

이 문서는 구현 순서와 완료 조건을 함께 정의한다. 각 번호를 하나의 작업 단위로 사용하고, 앞 번호의 완료 조건을 충족한 뒤 다음 번호로 이동한다.

다음 원칙은 전 과정에서 지켜야 한다.

1. 센서 수집은 네트워크 상태와 무관하게 계속되어야 한다.
2. 서버가 ACK하지 않은 진동 윈도우는 삭제하거나 덮어쓰지 않는다.
3. 같은 윈도우를 재전송할 때 `deviceId`, `bootId`, `windowIndex`, 타임스탬프, 품질, 샘플은 바뀌면 안 된다.
4. 이상 판단은 서버의 RF66 판정을 대체하지 않는다. 장치 측 판단은 전송 우선순위만 결정한다.
5. 진행 중인 HTTPS 요청은 새 이상 징후가 생겨도 중단하지 않는다. 요청 완료 후 우선 큐를 처리한다.
6. 기존 오디오 동기화 수정, 텔레메트리 재생 제한, raw HTTPS 진단 로그를 보존한다.
7. 기존 LittleFS를 자동 포맷하지 않는다. 파티션 변경 전 백업 및 복구 절차가 확인되지 않으면 펌웨어를 실제 장치에 올리지 않는다.
8. 이 문서에서 요구하지 않은 서버 API, RF66 알고리즘, 센서 샘플링 조건은 변경하지 않는다.

## 1. 구현 목표와 비목표

### 1.1 구현 목표

1. ADXL345 진동 데이터를 800 Hz, XYZ 각 512샘플 단위로 계속 수집한다.
2. 생성된 모든 raw 진동 윈도우를 네트워크 전송 전에 LittleFS에 영속 저장한다.
3. 정상 상태에서는 300,000 ms마다 전송 대상을 확정하고, 요청당 최대 4개 윈도우를 전송한다.
4. 이상 징후가 감지되면 5분 타이머를 기다리지 않고 관련 윈도우를 우선 전송한다.
5. HTTPS 실패, 타임아웃, 응답 파싱 실패, ACK 불일치 시 원본을 보존하고 재시도한다.
6. 재부팅 후에도 저장된 윈도우를 식별자와 시간 정보 그대로 복원해 전송한다.
7. health와 telemetry는 raw 저장·선별 과정과 분리하되, 실제 TLS 요청은 기존 네트워크 소유 태스크에서 직렬화한다.
8. 서버가 요구하는 `transmission` 메타데이터를 raw 요청 최상위에 추가한다.

### 1.2 이번 변경의 비목표

1. RF66 또는 서버 이상 판정 로직을 ESP32로 옮기지 않는다.
2. MQTT, HTTP/2, 다중 동시 TLS 연결을 새로 도입하지 않는다.
3. raw, telemetry, health를 각각 별도 네트워크 태스크에서 동시에 보내지 않는다.
4. 오디오 원본의 영속 저장 정책을 새로 만들지 않는다. 오디오는 현재의 best-effort 메타데이터 정책을 유지한다.
5. 저장소 전체를 일반화한 데이터베이스 계층이나 추상 인터페이스를 만들지 않는다.

## 2. 현재 구조와 목표 구조

### 2.1 현재 확인된 구조

현재 펌웨어는 다음 특성을 가진다.

1. raw 큐와 pending 큐의 기본 용량이 각각 8개이고, raw spool은 16개 슬롯이다.
2. raw 데이터는 pending이 가득 찰 때 주로 LittleFS로 넘겨진다. 모든 윈도우가 전송 전에 영속 저장되는 구조는 아니다.
3. pending 데이터가 있으면 5분 주기와 관계없이 raw HTTPS 요청을 시작한다.
4. 한 raw 요청은 최대 4개 윈도우를 담는다.
5. 특징값은 축당 7개이며 AC RMS는 `values[0]`, `values[7]`, `values[14]`, AC peak는 `values[1]`, `values[8]`, `values[15]`에 있다.
6. 품질 상태는 `Valid`, `FifoOverrun`, `SensorUnavailable`, `SampleGap`, `Clipped`, `ConstantAxis`, `ProcessingOverflow`를 사용한다.
7. raw 요청 본문에는 현재 `windows`만 있고 제안서의 `transmission` 객체는 없다.
8. 현재 브랜치에는 제안서가 언급한 `feat/adaptive-https-transmission` 및 `348f1ce` 참조가 없다. 원격에서 가져올 수 있는지 먼저 확인해야 하며, 확인 없이 기존 코드를 덮어쓰면 안 된다.

### 2.2 목표 데이터 흐름

```text
센서 수집
  -> 윈도우 처리 및 기존 특징 계산
  -> 전송 우선순위 판정
  -> 저장 요청 큐
  -> LittleFS에 윈도우 1건을 완전히 기록
  -> 저장 완료 목록에 등록
  -> 전송 스케줄러가 batch 선택
  -> 기존 단일 networkTask가 HTTPS 수행
  -> HTTP 및 ACK 검증
  -> ACK된 파일만 삭제
```

health와 telemetry는 별도 데이터 큐를 유지하되 HTTPS 호출 자체는 `networkTask`가 소유한다. 이것은 TLS 객체와 LittleFS 파일 핸들의 동시 접근을 줄이고, 세 요청이 동시에 TLS handshake를 발생시키는 병목을 막기 위한 것이다.

## 3. 구현 전에 확정할 입력값과 안전 게이트

### 3.1 서버 응답 계약 확인

서버는 변경된 요청을 받을 준비가 되었더라도 실제 응답 JSON 예제를 확보해 테스트 fixture로 저장해야 한다.

반드시 확인할 응답은 다음 두 가지다.

1. 신규 저장: HTTP 202, 요청한 각 윈도우의 ACK 식별자 목록
2. 중복 저장: HTTP 200, 이미 저장된 각 윈도우의 ACK 식별자 목록

현재 펌웨어는 `accepted`를 boolean으로 가정하는 경로가 있고, 기존 서버 구현은 이를 정수 건수로 반환한 이력이 있다. 따라서 `accepted == true`만 검사하는 코드는 먼저 제거해야 한다. 삭제 기준은 `accepted`의 자료형이 아니라 ACK 목록에 요청한 `(deviceId, bootId, windowIndex)`가 정확히 포함되었는지 여부다.

완료 조건:

- 서버의 202/200 실제 응답 예제를 확보했다.
- ACK 목록의 정확한 필드명과 자료형을 문서화했다.
- 신규 및 중복 응답 모두에 대한 파서 테스트가 있다.

### 3.2 기준값 확정

다음 값은 장치별 로컬 파일에서 제공한다.

```cpp
#define ADAPTIVE_BASELINE_ID "..."
#define ADAPTIVE_RMS_LOW_G ...
#define ADAPTIVE_RMS_HIGH_G ...
#define ADAPTIVE_SEVERE_LOW_G ...
#define ADAPTIVE_SEVERE_HIGH_G ...
#define ADAPTIVE_SEVERE_PEAK_G ...
#define ADAPTIVE_RECOVERY_MS 30000
```

유효 조건은 다음과 같다.

```text
0 <= severeLow < low < high < severeHigh
severePeak > 0
모든 진동 기준값 단위 = g
```

실측 기준값이 없으면 임의 숫자를 운영 기본값으로 넣지 않는다. 대신 `baselineId=unconfigured`로 동작하며 `baseline_missing` 사유로 짧고 제한된 주기의 전송을 수행한다.

### 3.3 파티션 및 OTA 결정

제안서의 N8 권장안은 앱 약 3.19 MiB, LittleFS 약 4.69 MiB, 768 슬롯이며 두 번째 OTA 앱 슬롯을 제거한다. 현재 로컬 파티션은 제안서에 적힌 과거 1.5 MiB와 다를 수 있으므로 실제 CSV 오프셋을 기준으로 다시 계산한다.

다음 중 하나가 결정되기 전에는 파티션을 적용하지 않는다.

1. OTA를 포기하고 단일 앱 + 대형 LittleFS를 사용한다.
2. OTA를 유지하고 저장 슬롯 수를 줄인다.

파티션 변경은 LittleFS 내용을 지울 수 있다. 장치의 미ACK 데이터를 서버 또는 PC에 백업하고 복원 검증을 마친 뒤에만 업로드한다.

## 5. 작업 02 — raw ACK 검증을 먼저 수정

### 목적

HTTP 성공인데 ACK 파싱 실패로 파일이 계속 쌓이는 문제를 제거한다. 이 작업이 끝나지 않으면 5분 저장 정책을 구현해도 저장소가 결국 포화된다.

### 구현 지침

1. raw 응답 파싱 함수를 한 곳으로 모으되, 새 클래스나 범용 JSON 계층은 만들지 않는다.
2. 요청을 만들 때 batch의 식별자 목록을 고정한다.
3. HTTP 202 또는 200 응답을 파싱한다.
4. 응답 ACK 목록에서 요청한 모든 `(deviceId, bootId, windowIndex)`가 정확히 한 번 이상 확인될 때만 batch 성공으로 처리한다.
5. 다음 경우에는 파일을 삭제하지 않는다.
   - HTTP 음수 오류 또는 2xx 이외 상태
   - JSON 파싱 실패
   - 장치 ID 불일치
   - boot ID 불일치
   - 일부 windowIndex 누락
   - 요청하지 않은 ACK만 존재
6. `accepted`가 boolean 또는 정수여도 ACK 목록이 정확하면 처리할 수 있게 한다. `accepted` 값만으로 삭제하지 않는다.
7. 삭제 도중 일부만 성공하면 성공한 파일만 제거하고 실패한 파일은 남긴다. 삭제 결과도 로그에 남긴다.

### 최소 테스트

1. HTTP 202 + 신규 4건 ACK → 4건 삭제 가능
2. HTTP 200 + 중복 4건 ACK → 4건 삭제 가능
3. HTTP 202 + ACK 3건 → 0건 batch 성공, 누락 식별자 로그
4. 잘못된 bootId → 삭제 금지
5. 깨진 JSON → 삭제 금지

### 완료 조건

- 신규와 중복 응답 모두 실제 서버 fixture로 통과한다.
- ACK가 불완전한 테스트에서 저장 데이터가 남아 있다.

## 6. 작업 03 — TLS와 LittleFS 소유권 안정화

### 목적

HTTPS 객체 소멸과 LittleFS 파일 close가 겹쳐 발생한 재부팅/assert 가능성을 제거한다.

### 구현 지침

1. `HTTPClient`, `WiFiClientSecure`, 응답 body, LittleFS 파일의 생성·종료 순서를 현재 호출 경로 전체에서 확인한다.
2. HTTPS 클라이언트는 기존 `networkTask`만 생성·사용·종료한다.
3. storage task는 HTTPS 객체에 접근하지 않고, network task는 열린 저장 파일 핸들을 장시간 보유하지 않는다.
4. 전송할 파일은 짧게 열어 RAM의 batch buffer에 읽고 즉시 닫은 뒤 HTTPS를 시작한다.
5. ACK 후 삭제도 HTTP 응답 body를 모두 읽고 `HTTPClient::end()`가 끝난 다음 수행한다.
6. `syncTimeFromBackend()`, raw, telemetry, health의 종료 경로가 같은 소유권 규칙을 지키게 한다.
7. 실패 경로마다 `end()`와 파일 close가 한 번만 실행되는지 확인한다.

### 완료 조건

- 부팅 직후 시간 동기화와 raw 전송을 반복해도 `lfs_file_close` assert와 재부팅이 없다.
- 모든 TLS 요청은 하나의 태스크에서만 실행된다.
- 열린 파일 수가 요청 반복에 따라 증가하지 않는다.

6. 설정이 없거나 잘못되면 센서 수집을 멈추지 않는다. `baseline_missing` 안전 모드로 들어가고 한 번의 명확한 오류 로그를 남긴다.

### 완료 조건

- 임계값 순서가 잘못된 빌드 또는 부팅이 명확하게 실패/안전 전환된다.

## 8. 작업 05 — 전송 우선순위 판정기 구현

### 목적

기존 특징값을 재사용해 순수한 상태 판정만 추가한다. FFT나 특징 계산을 다시 수행하지 않는다.

### 입력 계산

```cpp
compositeRmsG = sqrt(rmsX * rmsX + rmsY * rmsY + rmsZ * rmsZ);
maxPeakG = max(peakX, max(peakY, peakZ));
```

기존 배열에서는 다음 값을 사용한다.

```text
rmsX=values[0],  rmsY=values[7],  rmsZ=values[14]
peakX=values[1], peakY=values[8], peakZ=values[15]
```

### 판정 우선순위

1. 품질이 `Valid`가 아님 → 즉시 `priority / quality`
2. `compositeRmsG <= severeLow` 또는 `>= severeHigh`, 또는 `maxPeakG >= severePeak` → 즉시 `priority / severe`
3. 최근 연속 3개 유효 윈도우 중 2개 이상이 low 조건 → `priority / rms_low`
4. 최근 연속 3개 유효 윈도우 중 2개 이상이 high 조건 → `priority / rms_high`
5. baseline 누락/무효 → `priority / baseline_missing`
6. 이상 해제 후 정상 복귀 대기 중 → `priority / recovery_hold`
7. 저장 압력에 의한 조기 전송 → `periodic / storage_pressure`
8. 그 외 → 정상 periodic 대상

low 조건은 `compositeRmsG <= rmsLow`, high 조건은 `compositeRmsG >= rmsHigh`로 정의한다. 실제 경계 포함 여부는 서버/제안서와 한 번 확정한 뒤 테스트에 고정한다.

### 상태 리셋 조건

2-of-3 이력은 다음 경우 즉시 비운다.

1. 재부팅
2. windowIndex 불연속
3. 윈도우 타임스탬프 불연속
4. invalid quality

### 정상 복귀 조건

1. 이상 조건이 사라져도 즉시 periodic으로 돌아가지 않는다.
2. 유효하고 정상인 윈도우의 타임스탬프가 연속 30초를 채워야 한다.
3. invalid 또는 시간/index gap이 발생하면 정상 연속 시간을 다시 0으로 만든다.
4. `millis()` 경과가 아니라 윈도우에 기록된 시간 차로 계산한다.

### 구현 형태

판정기는 센서, 파일, HTTP에 접근하지 않는 작은 순수 함수/상태 구조로 만든다. 입력은 특징값·품질·index·timestamp이고 출력은 `mode`, `reason`, 상태 전환 여부다. 기존 특징 구조를 그대로 받아 불필요한 중간 모델은 만들지 않는다.

### 최소 테스트

1. 정상 10개 → priority 없음
2. low 1개 후 정상 → priority 없음
3. low, 정상, low → `rms_low`
4. high, high → `rms_high`
5. severe 1개 → 즉시 `severe`
6. invalid 1개 → 즉시 `quality`, 2-of-3 이력 초기화
7. index gap → 이력 초기화
8. 정상 29초 → hold 유지, 정상 30초 → periodic 복귀

## 9. 작업 06 — 윈도우 영속 저장 형식 확장

### 목적

모든 raw 윈도우를 전송 전에 저장하고 재부팅 후 동일하게 복원한다.

### 저장 레코드 필수 항목

1. 형식 version과 magic
2. CRC 또는 현재 저장 형식의 무결성 값
3. `deviceId`
4. `bootId`
5. `windowIndex`
6. UTC timestamp와 UTC 유효 여부
7. 샘플링 속도와 샘플 수
8. quality
9. XYZ raw samples
10. priority 여부와 trigger reason
11. 생성 당시 누적 drop 카운터에 필요한 정보

오디오가 best-effort라면 오디오 누락 때문에 진동 윈도우 저장을 실패시키지 않는다.

### 호환성 지침

1. 현재 v2 spool 파일을 읽을 수 있는 경로를 유지한다.
2. 새 형식을 v3로 추가하되 기존 파일을 부팅 시 일괄 재작성하지 않는다.
3. v2는 읽어서 전송하고, 새로 생성되는 데이터만 v3로 기록한다.
4. 알 수 없는 version 또는 CRC 오류 파일은 자동 삭제하지 않고 격리/오류 카운터로 노출한다.
5. 과거 boot에서 UTC가 확정되지 않은 레코드는 보존하되 자동 전송 대상에서 제외하고 `Preserved unresolved UTC`를 한 번 요약 로그로 남긴다.
6. 48시간을 넘긴 데이터는 타임스탬프를 현재로 바꾸지 않는다. 보존하고 수동 처리 대상으로 표시한다.

### 쓰기 안전성

1. 임시 슬롯에 header+body를 쓴다.
2. flush/close한다.
3. 다시 열어 magic/version/길이/CRC를 확인한다.
4. 검증 완료 후에만 저장 완료 목록에 등록한다.
5. 미ACK 파일이 있는 슬롯을 새 파일로 덮어쓰지 않는다.

### 완료 조건

- 전원 차단을 저장 단계별로 반복해도 정상 파일 또는 감지 가능한 불완전 파일만 남는다.
- 재부팅 후 식별자, 시간, 품질, 샘플이 바뀌지 않는다.
- v2 파일이 남아 있어도 부팅과 전송이 가능하다.

## 10. 작업 07 — 전용 storage task 도입

### 목적

센서 처리와 flash I/O를 분리하면서도 모든 윈도우가 전송 전 저장되도록 한다.

### 구현 지침

1. processing task는 특징과 전송 판정 결과를 만든 뒤 storage queue에 한 번 넣는다.
2. storage task는 큐에서 받아 파일을 기록하고 검증한 뒤 저장 완료 인덱스에 등록한다.
3. network task는 저장 완료된 레코드만 선택한다. RAM에만 있는 윈도우를 직접 전송하지 않는다.
4. storage queue가 가득 차면 같은 윈도우를 반복 FFT 처리하는 루프를 만들지 않는다.
5. 계산이 끝난 레코드는 하나의 hold 위치에 유지하고 큐 공간이 생기면 그대로 재시도한다.
6. RAM hold까지 가득 차고 새 센서 윈도우를 보존할 수 없을 때만 vibration drop을 증가시킨다.
7. drop이 발생하면 windowIndex를 재사용하지 않아 서버에서 gap을 확인할 수 있게 한다.

### 태스크 소유권

```text
capture task    : 센서 버퍼와 윈도우 생성
processing task : 특징 계산과 priority 판정
storage task    : LittleFS 생성/검증/목록 갱신
network task    : TLS, HTTP, ACK 검증 요청
```

파일 삭제는 network task가 직접 하지 않고 storage task에 ACK된 식별자 삭제 요청을 보내는 방식이 가장 안전하다. 기존 코드 변경량이 과도해진다면 HTTP 객체가 완전히 종료된 후 짧은 동기 삭제를 허용하되, 동시에 storage write가 수행되지 않도록 기존 mutex 한 개를 재사용한다.

### 완료 조건

- pending full 상태에서도 같은 `windowIndex`의 특징 계산 로그가 반복되지 않는다.
- 네트워크를 끊고 센서 수집을 계속했을 때 저장 용량까지 순서대로 쌓인다.
- 네트워크 복구 후 저장된 순서와 식별자가 유지된다.

## 11. 작업 08 — 5분 periodic 스케줄러 구현

### 목적

정상 상태의 네트워크 요청을 5분 경계로 묶되 수집을 막지 않는다.

### 구현 지침

1. `PERIODIC_UPLOAD_MS = 300000`을 정책 상수로 둔다.
2. 5분이 되면 그 시점까지 저장 완료된 마지막 레코드를 cutoff로 고정한다.
3. periodic 요청은 cutoff 이하의 레코드만 선택한다.
4. 한 요청에는 최대 4개 윈도우만 담는다.
5. cutoff backlog를 처리하는 동안 새로 생성된 정상 윈도우는 다음 5분 묶음에 남긴다.
6. 전송 중 priority가 발생하면 현재 요청을 끝낸 뒤 priority를 먼저 처리한다.
7. periodic backlog가 길어도 health가 영구 starvation되지 않게 기존 보조 요청 기회를 유지한다. 단, raw priority가 있을 때는 raw를 우선한다.
8. 재부팅에서 복원한 전송 가능 파일은 `replay` mode로 선택하며, UTC 유효성 확인 후 전송한다.

### 스케줄러 우선순위

```text
1. 현재 진행 중인 요청 완료
2. priority 대상
3. storage_pressure 조기 전송 대상
4. 확정된 periodic cutoff 대상
5. telemetry replay 1건
6. health/기타 보조 요청
```

보조 요청의 정확한 순서는 기존 서버 요구 주기를 해치지 않는 범위에서 현재 `serviceNetworkAuxiliary()`를 재사용한다. 별도 스케줄러 프레임워크를 만들지 않는다.

### 완료 조건

- 정상 10분 시험에서 5분 전에는 정상 raw 요청이 발생하지 않는다.
- 각 요청의 window 수는 1~4다.
- 첫 cutoff 이후 생성된 정상 윈도우가 첫 batch에 섞이지 않는다.

## 12. 작업 09 — priority 윈도우 선택 및 순서 구현

### 목적

이상 발생 전후 문맥을 일반 backlog보다 먼저 보낸다.

### 구현 지침

1. trigger 발생 시 아직 ACK되지 않은 직전 최대 3개 윈도우를 priority 대상으로 표시한다.
2. trigger/current 윈도우를 priority로 표시한다.
3. recovery hold 동안 생성되는 후속 윈도우도 priority 대상으로 표시한다.
4. 동일 파일을 periodic과 priority용으로 복사하지 않는다. 하나의 저장 레코드에 선택 상태만 둔다.
5. priority 내부 순서는 `(bootId의 생성 순서, windowIndex)`의 시간 순서를 유지한다.
6. 한 요청은 최대 4개이므로 앞선 3개 + trigger 1개를 첫 요청으로 보낼 수 있다.
7. trigger가 연속 발생하면 이미 표시된 레코드는 중복 등록하지 않는다.
8. 이전 periodic 요청이 진행 중이면 취소하지 않는다. 완료 직후 priority selector를 다시 실행한다.
9. ACK된 priority 파일만 삭제한다. 실패하면 같은 식별자와 payload로 다시 시도한다.

### 완료 조건

- backlog가 있는 상태에서 이상을 만들면 다음 요청이 오래된 periodic backlog가 아니라 priority 범위를 선택한다.
- 전송 중 이상 발생 시험에서 진행 요청은 정상 완료되고, 바로 다음 요청이 priority다.
- 재시도 payload의 윈도우 식별자와 샘플 hash가 동일하다.

## 13. 작업 10 — 요청 메타데이터 추가

### 요청 형식

기존 endpoint와 인증은 유지한다.

```http
POST /api/devices/{deviceId}/raw-vibration-windows
Authorization: Bearer ...
Content-Type: application/json
```

```json
{
  "windows": [
    "기존 윈도우 객체, 최대 4개"
  ],
  "transmission": {
    "policyId": "edge-trigger-batch-v1",
    "mode": "periodic",
    "reason": "none",
    "baselineId": "actual-baseline-id-or-unconfigured",
    "droppedWindows": 0
  }
}
```

### 허용값

`mode`:

- `periodic`
- `priority`
- `replay`

`reason`:

- `none`
- `rms_low`
- `rms_high`
- `severe`
- `quality`
- `baseline_missing`
- `storage_pressure`
- `recovery_hold`

### 구현 지침

1. 기존 windows 직렬화 코드를 재사용하고 최상위 `transmission`만 추가한다.
2. batch를 시작할 때 windows와 transmission 값을 모두 고정한다.
3. 같은 batch의 네트워크 재시도에서는 `droppedWindows`를 포함한 메타데이터도 바꾸지 않는다.
4. 새 batch를 만들 때만 최신 누적 drop 값을 넣는다.
5. 여러 priority reason이 섞이면 가장 높은 판정 우선순위를 대표 reason으로 사용한다.
6. storage pressure는 이상 판단이 아니므로 `mode=periodic`, `reason=storage_pressure`로 보낸다.
7. 과거 재부팅에서 복원한 정상 파일은 `mode=replay`로 보낸다. 복원 파일이 원래 priority 표식을 가지고 있다면 `mode=priority`를 유지한다.

### 완료 조건

- 서버가 periodic, priority, replay 예제를 모두 200/202로 수락한다.
- 재시도 전후 요청 body hash가 같다.
- `baselineId`와 누적 drop 카운터가 실제 상태와 일치한다.

## 14. 작업 11 — 저장 압력과 보존 정책 구현

### 목적

네트워크 장기 장애에서 데이터 유실을 숨기지 않고 가능한 범위까지 보존한다.

### 구현 지침

1. 사용 슬롯이 600개 이상이면 5분을 기다리지 않고 `storage_pressure` 전송을 시작한다.
2. priority 데이터가 있으면 storage pressure보다 먼저 보낸다.
3. 저장 공간이 가득 차도 미ACK 슬롯을 덮어쓰거나 자동 포맷하지 않는다.
4. flash가 가득 찬 뒤 RAM queue와 hold까지 모두 차서 새 윈도우를 저장할 수 없을 때만 drop한다.
5. drop 카운터는 현재 부팅 동안 누적하며 새 batch의 `droppedWindows`에 포함한다.
6. windowIndex는 drop된 경우에도 계속 증가시켜 gap을 남긴다.
7. 48시간보다 오래된 레코드는 자동 삭제 또는 시간 변경하지 않는다. 로그와 health에서 수량을 노출한다.
8. UTC 미확정 레코드는 보존하되 자동 전송하지 않고 별도 수량으로 노출한다.

### 주의

600 슬롯 임계값은 768 슬롯 파티션 프로필을 적용할 때의 값이다. 실제 슬롯 수가 달라지면 절대값을 그대로 쓰지 말고 `min(600, totalSlots의 안전 여유를 남기는 값)`으로 빌드 시 확정한다. 런타임의 복잡한 비율 계산은 필요 없다.

### 완료 조건

- 600 슬롯 도달 시험에서 다음 요청 reason이 `storage_pressure`다.
- full 상태에서 기존 파일 hash가 바뀌지 않는다.
- drop과 index gap이 서버 및 장치 로그에서 확인된다.

## 15. 작업 12 — N8 adaptive 파티션 프로필 추가

### 목적

5분 분량과 장애 여유를 담을 수 있는 실제 저장 공간을 제공한다.

### 구현 지침

1. 현재 파티션 CSV의 모든 시작 주소, 크기, 8 MiB flash 경계를 계산해 겹침이 없는지 확인한다.
2. 기존 environment를 바로 바꾸지 말고 별도 adaptive environment를 추가한다.
3. 목표는 제안서 기준 앱 약 3.19 MiB, LittleFS 약 4.69 MiB, 768 슬롯이다.
4. 새 environment에서는 PSRAM이 없어도 필수 진동 수집·저장·전송이 동작해야 한다.
5. 파티션 CSV가 `.gitignore`의 `*.csv`에 막히면 해당 파일만 명시적으로 추적하거나 제한된 예외 규칙을 추가한다.
6. `ALLOW_EMPTY_LITTLEFS_FORMAT=1` 같은 자동 포맷 플래그는 adaptive 운영 프로필에서 제거한다.
7. 업로드 전 다음 절차를 문서화하고 실제 장치에서 확인한다.
   - 미ACK 파일 수 확인
   - 기존 파티션 데이터 백업
   - 백업 파일 hash 기록
   - 새 파티션 펌웨어 업로드
   - 필요 데이터 복원
   - 복원 후 hash 및 전송 확인
8. OTA 제거가 확정되지 않았다면 새 프로필을 기본값으로 승격하지 않는다.

### 용량 검증

다음을 빌드 산출물로 기록한다.

1. 앱 binary 실제 크기와 app partition 여유
2. LittleFS 실제 크기
3. 윈도우 레코드 1개의 실제 byte 수
4. 실제 생성 가능한 슬롯 수
5. 469개 윈도우 저장 후 잔여 공간

### 완료 조건

- partition overlap 없이 N8 빌드가 성공한다.
- 469개 이상 저장 후 mount/reboot/read가 성공한다.
- 자동 포맷 없이 손상 상태를 오류로 보고한다.
- OTA 유지 여부가 명시적으로 기록되어 있다.

## 16. 작업 13 — 진단 로그와 health 지표 정리

### 목적

로그만으로 수집, 저장, 선택, HTTPS, ACK, 삭제의 인과관계를 재구성할 수 있게 한다.

### batch 공통 식별자

각 요청에 짧은 `batchId`를 부여하고 아래 로그에 동일하게 넣는다.

1. batch 선택
2. HTTP 시작/종료
3. ACK 파싱
4. 파일 삭제
5. 재시도

### 필수 로그 항목

1. bootId
2. 시작/끝 windowIndex와 count
3. quality 요약
4. mode와 reason
5. HTTP status, request/body-read/total ms
6. 서버 ACK index 목록 또는 범위
7. 저장 pending, RAM pending, drop 누계
8. FIFO max gap
9. free heap과 largest free block
10. 각 태스크 stack high-water mark
11. UTC unresolved 및 48시간 초과 보존 수량

### 로그 억제

`pending_full`, 오디오 누락, unresolved UTC 같은 반복 상태는 매 윈도우 출력하지 않는다. 상태 최초 1회, 누적값 변경 요약, 또는 제한된 주기마다 출력한다. 카운터 자체는 계속 정확히 증가시킨다.

### 권장 로그 예

```text
[TX-SELECT] batch=42 mode=priority reason=rms_high boot=... index=120-123 count=4 stored=511 dropped=0
[HTTP-DIAG] batch=42 op=raw status=202 request_ms=... total_ms=...
[TX-ACK] batch=42 expected=4 matched=4 indexes=120,121,122,123
[STORE-DELETE] batch=42 removed=4 failed=0 remaining=507
```

### 완료 조건

- 5분 로그에서 한 윈도우가 생성되어 저장되고 선택·ACK·삭제되는 흐름을 추적할 수 있다.
- 동일 경고가 초당 여러 번 반복되어 핵심 로그를 가리지 않는다.

## 17. 작업 14 — 테스트 계획

### 17.1 호스트 단위 테스트

다음 로직은 하드웨어 없이 테스트한다.

1. composite RMS와 max peak 계산
2. 2-of-3 low/high 판정
3. severe 및 quality 즉시 판정
4. discontinuity reset
5. 30초 recovery
6. periodic cutoff 선택
7. priority 앞 3개 선택 및 중복 방지
8. ACK 목록 완전 일치 검증
9. 저장 header/version/CRC 읽기
10. 요청 metadata 직렬화

기존 테스트 구조를 재사용하고 새 테스트 프레임워크를 추가하지 않는다.

### 17.2 서버 계약 테스트

1. periodic/none 요청
2. priority/rms_high 요청
3. priority/quality 요청
4. replay 요청
5. 같은 body 재전송에 대한 HTTP 200 duplicate ACK
6. 과거 windowIndex gap을 포함한 periodic/replay 수락
7. 잘못된 metadata enum 거절 확인

### 17.3 장치 통합 테스트

| 번호 | 시나리오 | 기대 결과 |
|---:|---|---|
| 1 | 정상 10분 | 5분 단위 cutoff, 요청당 최대 4개, drop 0 |
| 2 | 작은 변화 1회 | priority 없음 |
| 3 | 최근 3개 중 low/high 2회 | 즉시 해당 priority reason |
| 4 | severe 1회 | 즉시 `severe` |
| 5 | 센서 분리/invalid | 즉시 `quality`, 이력 reset |
| 6 | 이상 후 정상 30초 | 30초 동안 hold, 이후 periodic 복귀 |
| 7 | periodic 요청 중 이상 | 요청 중단 없음, 다음 batch priority |
| 8 | Wi-Fi 단절/HTTP timeout | 파일 보존, 복구 후 동일 식별자로 재전송 |
| 9 | ACK 일부 누락 | 어떤 요청 파일도 잘못 삭제하지 않음 |
| 10 | 저장/전송 중 재부팅 | mount 성공, 식별자와 hash 보존 |
| 11 | 600 슬롯 도달 | `storage_pressure` 조기 전송 |
| 12 | 저장소 full | 미ACK overwrite 없음, 불가피한 drop만 카운트 |
| 13 | 48시간 초과 데이터 | 자동 삭제/시간 변경 없음 |
| 14 | UTC 미확정 과거 데이터 | 보존, 자동 전송 제외, 요약 로그 |

### 17.4 빌드 및 실행 게이트

최소 실행 항목은 다음과 같다.

```powershell
pio test -e native
pio run -e esp32-s3-devkitc-1-n8
pio run -e <새 adaptive N8 environment>
```

로컬에 native compiler가 없다면 그 사실을 기록하고 CI 또는 설치된 환경에서 같은 테스트를 통과시킨다. 빌드 성공만으로 완료 처리하지 않는다.

## 18. 작업 15 — 단계별 장치 적용 순서

실제 장치에는 다음 순서로 적용한다.

1. ACK 파서와 TLS/LittleFS 안정화만 적용한다.
2. 기존 파티션에서 5분 이상 시험해 재부팅과 잘못된 삭제가 없는지 확인한다.
3. 판정기와 요청 metadata를 적용하고 서버 계약을 확인한다.
4. 모든 윈도우 영속 저장과 5분/priority 스케줄러를 적용한다.
5. 네트워크 단절 및 전원 차단 시험을 통과한다.
6. 기존 LittleFS를 백업한다.
7. OTA 결정이 완료된 adaptive 파티션을 적용한다.
8. 정상 10분, 이상, 복구, 저장 압력 시험을 실행한다.
9. 5분 전체 로그를 분석해 drop, 반복 로그, 요청 순서, ACK 인과관계를 확인한다.

각 단계에서 실패하면 다음 단계로 넘어가지 않는다. 특히 파티션 변경 실패를 응용 코드 문제와 섞지 않는다.

## 19. 권장 변경 묶음

리뷰와 원인 추적이 가능하도록 변경을 다음 단위로 나눈다.

1. `ACK 계약 수정 + 테스트`
2. `TLS/LittleFS 소유권 안정화`
3. `adaptive 설정 + 순수 판정기 + 테스트`
4. `v3 영속 형식 + storage task + 전원 차단 테스트`
5. `periodic/priority 스케줄러 + transmission metadata`
6. `저장 압력/보존 정책 + 진단 로그`
7. `adaptive N8 파티션 프로필 + 백업/복원 문서`

한 묶음에서 파티션, ACK, 판정기, 태스크 구조를 동시에 바꾸지 않는다. 실패 시 어느 층의 문제인지 구분할 수 있어야 한다.

## 20. 전체 완료 정의

다음 조건을 모두 만족해야 구현 완료로 본다.

1. 정상 상태 raw 전송은 5분 cutoff에 따라 시작한다.
2. 이상 조건은 정의된 1-window 또는 2-of-3 규칙으로 즉시 priority 전송된다.
3. 이상 전 최대 3개, trigger, 후속 recovery 윈도우가 backlog보다 우선한다.
4. 정상 30초 연속 후 periodic으로 복귀한다.
5. 서버의 신규 202와 중복 200 응답을 모두 정확히 ACK 처리한다.
6. 실패·타임아웃·부분 ACK·재부팅에서 미ACK 원본이 보존된다.
7. 요청 재시도에서 윈도우 식별자와 샘플, 고정된 body가 동일하다.
8. 600 슬롯 저장 압력과 full 동작이 데이터 덮어쓰기 없이 검증된다.
9. LittleFS assert, watchdog reset, 반복 FFT 처리, 과도한 반복 로그가 없다.
10. 센서 수집 조건 800 Hz/512 samples와 기존 특징 계산 결과가 유지된다.
11. health와 telemetry가 장기 starvation되지 않으며 TLS 호출은 한 태스크에서 직렬화된다.
12. 실제 장치의 10분 정상 시험과 제17장의 이상/장애 시험 결과가 기록되어 있다.

## 21. 착수 전에 남은 확인 항목

다음 네 항목은 구현자가 임의로 결정하지 말고 담당자 확인값을 기록한다.

1. 서버의 실제 202/200 ACK JSON 형식
