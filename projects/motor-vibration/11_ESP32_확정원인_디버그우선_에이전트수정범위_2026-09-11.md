## 01. 현재 확정된 문제

### 01-01. Drop의 직접 발생 지점

확정 근거:

1. capture는 512 samples를 800 Hz로 수집하므로 정상 window 생성 주기는 `512 / 800 = 0.64초`다.
2. `RawQueueCapacity=8`이므로 raw queue가 흡수할 수 있는 시간은 최대 `8 × 0.64 = 5.12초`다.
3. `finish()`의 `xQueueSend(rawQueue, &capturing, 0)`가 실패하면 `capture_queue_full`과 `processingDrops`가 증가한다.
4. 실제 로그에서 raw queue가 `0 -> 8`로 포화되고 `capture_queue_full`이 증가했다.

판정:

- `Dropped windows`의 직접 원인은 서버 ACK가 아니라 **processing이 5.12초 안에 raw queue를 비우지 못한 것**이다.

### 01-02. 첫 spool write의 slot scan이 queue 허용시간을 초과

확정 근거:

1. `rawSpoolNextSlot`은 부팅할 때 0으로 초기화된다.
2. `writeRawSpool()`은 cursor부터 빈 slot이 나올 때까지 `stat()`을 반복한다.
3. 실제 첫 write의 `storage_slot_lookup_us=8,796,622`, 즉 약 8.80초였다.
4. 8.80초는 raw queue 허용시간 5.12초보다 길다.

판정:

- 현재 cursor는 두 번째 write부터는 도움이 되지만 **재부팅 후 첫 write의 drop은 막지 못한다**.
- 첫 빈 slot scan은 capture task 시작 전 1회 수행하고 cursor를 설정해야 한다.

### 01-03. 최신 network 우선순위 guard가 backlog 전송을 차단

확정 근거:

1. network task는 batch 선택 직전에 다음 조건을 실행한다.

```cpp
if (!size && !rawQueueIsEmpty()) continue;
```

2. `rawQueueIsEmpty()`는 다음 세 조건이 모두 비어야 true다.
   - `pending`
   - `rawQueue`
   - `rawHold`
3. 연속 capture 중 processing이 늦어지면 셋 중 하나는 계속 차 있게 된다.
4. guard가 false가 아니면 `loadRawSpoolBatch()`와 pending 선택까지 도달하지 않는다.
5. 따라서 active batch가 없는 시점에는 이미 durable한 spool record도 새 HTTP batch로 선택되어 ACK 삭제될 기회를 얻지 못한다.

판정:

- 이 guard는 경쟁 완화가 아니라 **생산 backlog가 있을 때 새 소비 batch 선택을 중지시키는 확정 논리 오류**다.
- 해당 guard를 제거해야 한다. 같은 의미의 조건으로 대체하지 않는다.

### 01-04. processing mutex 범위가 filesystem write까지 포함

확정 근거:

1. `processingTask()`는 `mutex`를 잡은 뒤 `writeRawSpool(raw)`을 호출한다.
2. 실제 spool write는 첫 시도에서 약 11.05초가 걸렸다.
3. 같은 `mutex`는 pending 조회/선택 및 `rawQueueIsEmpty()`에서 사용한다.
4. `writeRawSpool()`이 사용하는 `raw`와 `features`는 processing task의 지역 데이터다.

판정:

- filesystem write 전체를 pending mutex로 보호할 이유가 없다.
- `raw.quality` 설정과 `writeRawSpool()`은 mutex 밖에서 수행하고, pending/latest 공유 상태 갱신 직전에만 mutex를 잡아야 한다.

### 01-05. LittleFS panic의 호출 경로

확정 근거:

1. panic은 `IntegerDivideByZero`였다.
2. 현재 ELF backtrace는 다음 순서로 해석됐다.
   - `lfs_alloc`
   - `lfs_dir_alloc` / directory commit
   - `lfs_file_sync_`
   - `vfs_littlefs_open`
   - `fopen`
   - `FS::open`
   - `ContinuousVibration::writeRawSpool()` line 406
   - `ContinuousVibration::processingTask()` line 954
3. 제품 코드의 마지막 호출은 `LittleFS.open(temp, "w")`다.
4. 당시 LittleFS는 total `2,752,512`, used `2,748,416`, free `4,096` bytes였다.
5. raw record 논리 크기는 header 61 + payload 3,072 = `3,133` bytes다.
6. 현재 admission은 `freeBytes < RawSpoolSlotBytes`만 검사하므로 free 4,096에서 통과한다.

판정:

- **현재 capacity admission이 실제 panic 상태 진입을 차단하지 못한다**는 것은 확정이다.
- 하지만 free 4,096이 allocator panic의 단독 원인인지, allocator state 손상인지, bundled LittleFS 결함인지는 아직 확정되지 않았다.

### 01-06. 반복 write 처리량도 capture 주기보다 느린 관찰값

확정 근거:

1. cursor 적용 뒤 slot lookup이 약 8~12 ms로 줄어든 write가 있었다.
2. 같은 구간의 `storage_total_us`는 약 1.1~1.5초였다.
3. 정상 window 생성 주기 0.64초보다 길다.

판정:

- 관찰된 조건에서는 file-per-window write 처리량이 capture를 따라가지 못했다.
- 다만 network 경쟁과 near-full 상태가 제거된 독립 측정이 없으므로 fixed ring 전환은 아직 승인하지 않는다.

## 02. 아직 확정되지 않은 문제

### 02-01. LittleFS allocator가 0으로 나눈 정확한 이유

현재 증거로 구분되지 않는 항목:

1. near-full allocation 경계 처리 문제
2. mount 이후 allocator state 손상
3. 동시 접근 또는 lock 순서 문제
4. 현재 bundled `esp_littlefs/littlefs` 버전 결함

주의:

- 일반 upstream littlefs allocator는 full scan 뒤 `LFS_ERR_NOSPC`를 반환하도록 작성되어 있다.
- 따라서 “디스크가 찼으므로 divide-by-zero가 정상적으로 발생했다”라고 결론 내리면 안 된다.
- bundled 바이너리에 대응하는 정확한 `lfs.c` revision과 line 689를 찾기 전에는 내부 divisor를 단정하지 않는다.

### 02-02. 안전한 free-space reserve 값

확정된 값:

- free `4,096` bytes 상태는 현재 firmware에서 안전하지 않았다.
- ESP32 esp_littlefs의 일반 block 크기는 4,096 bytes이고, 현재 total/used 값도 4,096 단위다.

미확정 값:

- temp create + directory metadata + rename에 필요한 최소 reserve block 수

판정:

- 8 KiB, 12 KiB 같은 임의 threshold를 최종 해결값으로 넣지 않는다.
- 첫 진단 firmware에서는 **이미 실패가 확인된 free <= 4,096 상태만 fail-closed로 차단하고, 해당 부팅 동안 새 raw spool write를 재개하지 않는다**.
- strict ACK로 기존 durable spool이 삭제되어 공간이 늘어도 같은 boot에서는 write suspension을 유지한다. 다음 부팅 전에 결과를 보고한다.

### 02-03. TLS `-1`의 하위 원인

확정된 내용:

1. `http.begin()`은 성공한 경우가 있고, `POST()`에서 HTTP 응답 전에 `-1`이 발생했다.
2. 동일 endpoint로 이후 HTTP 202가 성공한 이력이 있다.
3. 그러므로 URL, token, CA 설정을 영구 오설정으로 확정할 수 없다.

미확정 내용:

1. DNS 지연/실패
2. TCP connect/reset
3. TLS handshake 실패/timeout
4. Wi-Fi reconnect와의 시간 상관관계
5. reusable socket 상태

판정:

- timeout, retry, 인증서, socket reuse 정책을 바꾸지 않는다.
- DNS 결과와 실패 event ID를 추가해 다음 로그에서 범위를 줄인다.

### A1-04. 부팅 전 raw spool cursor 초기화

1. `ContinuousVibration::start()`에서 task 생성 전에 기존 slot을 1회 scan한다.
2. 첫 빈 slot을 `rawSpoolNextSlot`에 저장한다.
3. scan 시간, 확인한 slot 수, 선택 slot을 1줄로 출력한다.
4. 모든 slot이 차 있으면 `RawSpoolSlots` sentinel 상태를 별도로 기록한다.

예시:

```cpp
void initializeRawSpoolCursor() {
    const uint64_t startedUs = esp_timer_get_time();
    unsigned next = RawSpoolSlots;
    unsigned scanned = 0;
    {
        LittleFsLock fsLock;
        for (unsigned i = 0; i < RawSpoolSlots; ++i) {
            ++scanned;
            if (!rawSpoolPresent(rawSpoolPath(i))) {
                next = i;
                break;
            }
        }
    }
    rawSpoolNextSlot.store(next == RawSpoolSlots ? 0U : next,
                           std::memory_order_relaxed);
    Serial.printf("[RAW-SPOOL-BOOT] scanned=%u next=%u full=%s elapsed_us=%llu\n",
                  scanned, next, next == RawSpoolSlots ? "yes" : "no",
                  static_cast<unsigned long long>(esp_timer_get_time() - startedUs));
}
```

제약:

- scan은 capture/processing/network task 생성 전에 끝나야 한다.
- 새 metadata 파일이나 NVS cursor persistence는 이번 범위에서 추가하지 않는다.

### A1-05. 실패가 확인된 free-space 상태를 fail-closed로 격리

이 코드는 최종 reserve 결정이 아니라 panic 재현 상태를 피하면서 기존 spool을 drain하기 위한 진단 게이트다.

```cpp
constexpr size_t ObservedUnsafeRawSpoolFreeBytes = 4096U;
std::atomic<bool> rawSpoolWritesSuspended{false};

void initializeRawSpoolAdmission() {
    size_t total = 0;
    size_t used = 0;
    const esp_err_t rc = esp_littlefs_info("spiffs", &total, &used);
    const size_t free = rc == ESP_OK && total >= used ? total - used : 0;
    const bool suspend = rc != ESP_OK || free <= ObservedUnsafeRawSpoolFreeBytes;
    rawSpoolWritesSuspended.store(suspend, std::memory_order_release);
    Serial.printf("[RAW-SPOOL-ADMISSION] rc=%s total=%u used=%u free=%u suspended=%s reason=%s\n",
                  esp_err_to_name(rc), static_cast<unsigned>(total),
                  static_cast<unsigned>(used), static_cast<unsigned>(free),
                  suspend ? "yes" : "no",
                  rc != ESP_OK ? "info_failed" :
                  (suspend ? "observed_unsafe_state" : "none"));
}
```

`writeRawSpool()` 시작부에는 다음 진단 분기를 둔다.

```cpp
if (rawSpoolWritesSuspended.load(std::memory_order_acquire)) {
    ++dropMetrics.spool_capacity_full;
    return false;
}
```

제약:

1. suspension은 같은 boot에서 자동 해제하지 않는다.
2. 기존 spool read/HTTP send/strict ACK delete는 허용한다.
3. manual delete, oldest overwrite, format은 금지한다.
4. 이 분기로 panic이 사라져도 4,096 bytes가 panic의 단독 원인이라고 결론 내리지 않는다.

완료 조건:

- free <= 4,096 또는 info 실패 시 `LittleFS.open(temp, "w")`에 도달하지 않는다.
- 기존 durable spool 전송 경로는 살아 있다.

**Agent 2 중단선:** upload, timeout 조정, 인증서 변경, retry 조정, server 변경을 하지 않는다.

## 06. Coordinator 통합 순서

### C-01. 두 Agent 보고 수신

1. A1-01~A1-07을 번호별로 확인한다.
2. A2-01~A2-04를 번호별로 확인한다.
3. 미완료 번호가 있으면 통합하지 않는다.
4. Agent를 종료한 뒤 Coordinator가 최종 diff를 직접 읽는다.

### C-02. 필수 코드 리뷰

확인 항목:

1. network task batch 선택 앞의 `rawQueueIsEmpty()` 차단 guard가 제거됐는가.
2. `writeRawSpool()` 호출 중 pending `mutex`를 보유하지 않는가.
3. boot cursor scan이 task 생성 전에 끝나는가.
4. admission suspension 중 temp open이 불가능한가.
5. suspension 중 기존 spool read/send/ACK delete는 가능한가.
6. strict ACK 전 삭제가 없는가.
7. 새로운 lock inversion이 없는가.
8. TLS behavior 값이 바뀌지 않았는가.
9. 민감정보 출력이 없는가.

### C-03. 로컬 검증

1. native toolchain PATH를 먼저 복원한다.

```powershell
$env:Path = 'C:\msys64\ucrt64\bin;' + $env:Path
```

2. `pio test -e native`
3. `pio run -e esp32-s3-devkitc-1-n8`
4. 관련 파일 대상 `git diff --check`
5. 실패하면 upload하지 않고 해당 번호로 되돌려 보고한다.

### C-04. COM7 진단 firmware 1회 업로드

허용:

- `esp32-s3-devkitc-1-n8` firmware upload

금지:

- filesystem image upload
- format
- erase
- partition 변경

### C-05. 정확히 3분 로그 관찰

반드시 기록:

1. firmware ELF SHA
2. boot session ID
3. `[RAW-SPOOL-ADMISSION]`
4. `[RAW-SPOOL-BOOT]`
5. raw queue depth/high-water
6. `capture_queue_full`
7. storage timing bucket
8. spool batch 선택 및 HTTP attempt
9. strict ACK와 삭제
10. TLS event/DNS event
11. panic/watchdog/reboot

이번 3분 진단의 성공 조건:

1. `IntegerDivideByZero`, Guru Meditation, watchdog, reboot가 0이다.
2. admission suspension 상태에서도 network task가 기존 durable spool을 선택한다.
3. HTTP 200/202 + strict ACK가 오면 해당 spool만 삭제된다.
4. TLS `-1`이면 같은 event ID의 DNS 결과가 남는다.

주의:

- 이 진단 firmware는 새 raw write를 의도적으로 suspend할 수 있으므로 `Dropped windows=0`을 최종 성공 조건으로 사용하지 않는다.
- 목적은 panic 경로와 network drain 경로를 먼저 분리하는 것이다.

### C-06. 3분 후 반드시 중단하고 보고

3분 결과에 관계없이 다음 구현으로 넘어가지 않는다. 아래 결정표만 채운다.

| 관찰 결과 | 확정 가능한 결론 | 다음 행동 |
|---|---|---|
| suspension 중 panic 0, spool ACK 삭제 성공 | 기존 network guard가 drain을 막았음이 실장비에서도 확인됨 | 다음 문서에서 controlled write gate 설계 |
| suspension 중에도 같은 raw temp-open panic | 다른 write 경로가 suspension을 우회함 | backtrace line 확인 후 즉시 중단 |
| suspension 중 다른 LittleFS 경로 panic | raw create 단독 문제가 아님 | 해당 경로와 exact bundled source 확인 |
| DNS rc 실패 + TLS `-1` | DNS 실패가 해당 event의 직접 원인 | DNS event 반복성만 별도 검증 |
| DNS 성공 + TLS `-1` | DNS 이후 TCP/TLS/HTTP connect 구간 문제 | lower-level transport debug 계획 작성 |
| ACK가 없어 공간이 줄지 않음 | storage drain 검증 불가 | write suspension 유지, TLS 결과 보고 |

**Coordinator 중단선:** C-06 보고서 작성까지다. 같은 실행에서 fixed ring, reserve threshold 확대, framework/library upgrade, partition 변경을 하지 않는다.

## 07. 이번 범위 이후에만 결정할 항목

### NEXT-01. raw write 재개 threshold

조건:

1. bundled `esp_littlefs`의 exact source revision과 `lfs.c:689`를 확보한다.
2. allocator의 실제 divisor와 0이 된 상태값을 확인한다.
3. strict ACK drain 뒤 free block 수를 기록한다.

이 세 증거 전에는 최종 reserve 값을 정하지 않는다.

### NEXT-02. file-per-window 제거 여부

조건:

1. network 요청을 중지한 동일 firmware에서 측정한다.
2. near-full이 아닌 상태에서 연속 write p95/max를 측정한다.
3. `storage_total_us > 640,000`이 반복되면 file lifecycle 병목으로 확정한다.

확정될 때만 preallocated raw ring/fixed offset 설계를 별도 문서로 작성한다.

### NEXT-03. TLS 동작 수정 여부

조건:

1. DNS 실패인지 DNS 이후 실패인지 event ID로 분리한다.
2. Wi-Fi disconnect와 같은 시점인지 확인한다.
3. 같은 endpoint의 성공 event와 실패 event를 비교한다.

증거 전에는 timeout/retry/reuse/certificate를 바꾸지 않는다.

## 09. 참고 근거

1. 로컬 framework: `framework-arduinoespressif32 3.20017.241212` (Arduino core 2.0.17 계열)
2. 로컬 partition: `n8_raw_8MB.csv`, LittleFS partition `0x2A0000 = 2,752,512 bytes`
3. 로컬 SDK config: page 256, read 128, lookahead 128, cache 512
4. [esp_littlefs upstream 설명](https://github.com/joltwallet/esp_littlefs#tips-tricks-and-gotchas): ESP32 block size는 4,096 bytes이며 freshly formatted filesystem도 metadata block을 사용한다.
5. [upstream littlefs allocator](https://github.com/littlefs-project/littlefs/blob/master/lfs.c)는 공간을 모두 검사하면 `LFS_ERR_NOSPC`를 반환하도록 되어 있다. 현재 bundled binary의 exact revision과 line 번호가 확인되기 전에는 upstream 최신 소스를 현재 crash의 직접 증거로 사용하지 않는다.
