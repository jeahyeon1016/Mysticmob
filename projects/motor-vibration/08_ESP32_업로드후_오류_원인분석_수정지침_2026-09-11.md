## 2. 관측 사실과 추론 분리

### 2.1 확정된 사실

- 서버는 같은 boot stream에서 이미 받은 index 이하의 신규 window를 409로 거부한다.
- 펌웨어는 backlog의 낮은 index보다 높은 priority index를 먼저 전송할 수 있다.
- 펌웨어의 invalid baseline 경로는 모든 valid window를 priority로 반환한다.
- Raw RAM 경로는 `rawQueue=8`, `pending=8`, `rawHold=8`이다.
- Raw 파일 spool은 `RawSpoolSlots=16`이다.
- 네트워크 task는 선택된 batch만 TLS 직전에 spool에 저장한다. 아직 선택되지 않은 모든 window를 영속 저장하지 않는다.
- 실패 status의 종류와 관계없이 active batch를 유지하고 재시도 delay를 최대 500ms로 제한한다.

### 2.2 아직 확정되지 않은 사실

- 초기 TLS `status=-1`의 정확한 mbedTLS 원인은 현재 로그만으로 알 수 없다. 이후 같은 endpoint에서 202가 성공했으므로 인증서·URL의 영구 오류로 단정할 수 없다.
- 배포 서버가 로컬 `motor_diagnosis\vibration_windows.py`와 완전히 같은 revision인지는 확인되지 않았다. 다만 409 code와 message, 단조 index 동작은 일치한다.
- `no permits for creation`은 실제 저장 실패가 아니다. 현재 증거상 존재 여부 검사 과정의 VFS 오류 로그일 가능성이 높다.

## 3. 원인 우선순위

### RC-1 — priority 선택과 서버 stream 순서 계약의 충돌

신뢰도: 매우 높음

증거:

- `include\priority_selector.h`는 가장 최신 trigger와 앞선 최대 3개를 선택한다.
- `include\continuous_vibration_runtime.h`의 `selectPriorityPending()`가 이 결과를 periodic backlog보다 먼저 사용한다.
- 서버 계약은 같은 `(deviceId, bootId)`에서 신규 index가 기존 stream index보다 작거나 같으면 409다.
- 실제 로그에서 `7~14`가 먼저 ACK된 뒤 `5,6`이 포함된 batch가 409를 받았다.

결론:

현재 서버 계약을 유지하면서 `오래된 backlog보다 높은 priority index를 먼저 ACK`하고, 나중에 낮은 backlog도 전송하는 두 요구를 동시에 만족할 수 없다. 단순 정렬만으로 해결되지 않는다. 서버가 out-of-order 신규 window를 허용하거나, 펌웨어가 항상 가장 낮은 미ACK index부터 보내 priority 우선을 포기해야 한다.

### RC-2 — baseline_missing이 제한 전송이 아니라 무제한 priority로 동작

신뢰도: 매우 높음

증거:

- `src\adaptive_transmission.cpp`의 invalid config 분기는 매 window마다 `{Priority, BaselineMissing}`을 반환한다.
- 실장비에서 batch 1~3이 모두 `reason=baseline_missing` priority였다.
- 원 지침은 baseline 값이 없을 때 짧고 제한된 주기로 전송하도록 요구한다.

영향:

- 정상 5분 periodic 정책을 우회한다.
- 지속적으로 최신 trigger를 선택해 RC-1의 순서 역전을 확대한다.
- 네트워크 장애 시 큐를 빠르게 포화시킨다.

### RC-3 — 모든 Raw window가 ACK 전 영속 저장되지 않음

신뢰도: 매우 높음

증거:

- processing task는 먼저 RAM `pending`에 push한다.
- `writeRawSpool()`은 network task가 batch를 선택한 뒤에만 호출된다.
- pending이 차면 8개 rawHold를 사용하고, 그것도 차면 `processingDrops`를 증가시킨다.
- 첫 Raw 요청은 최대 약 24.6초가 걸렸고 640ms window 기준 약 38개가 생성될 수 있다.
- 현재 RAM 3단계의 명목 합계는 24개라 이 지연을 흡수하지 못한다.

결론:

TLS 실패가 직접적인 데이터 유실 원인은 아니다. 유실의 직접 원인은 네트워크보다 앞단에 충분한 durable queue가 없다는 것이다. RAM 크기만 늘리는 것은 재부팅과 장기 장애를 해결하지 못한다.

### RC-4 — 영구 409에도 500ms급 무한 재시도

신뢰도: 매우 높음

증거:

- 실패 분기의 delay는 `min(retryDelayMs, 500)`이고 다음 값도 최대 500으로 고정된다.
- HTTP 409도 다른 실패와 같은 분기로 들어간다.
- 실장비에서 같은 batch 4가 retry 35 이상 반복됐다.

영향:

- 영구적으로 성공할 수 없는 payload가 network task를 점유한다.
- pending을 비우지 못해 drop이 계속 증가한다.
- 로그와 서버 요청이 폭증한다.

### RC-5 — LittleFS 존재 검사 로그가 실제 실패처럼 보임

신뢰도: 높음

증거:

- 오류 직후 같은 slot의 `[RAW-SPOOL] stored`가 출력된다.
- 빈 slot 탐색에서 `LittleFS.exists()`를 반복 호출한다.

결론:

현재 데이터 유실의 주원인은 아니다. 그러나 실제 write 실패와 구별되지 않아 운영 판단을 방해하므로 로그를 정리해야 한다.

### RC-6 — 진단 로그의 의미가 불충분하거나 잘못됨

신뢰도: 높음

- `TX-SELECT index=first-last`는 비연속 batch `5,6,15,16`을 `5~16`으로 숨긴다.
- `STORE-DELETE remaining`은 삭제 전에 읽은 `pendingAfter`를 사용해 실제 삭제 후 개수와 다를 수 있다.
- `RAW-ATTEMPT raw_attempt=1`은 항상 1이고 실제 attempt 번호가 아니다.
- `[BUFFER] dropped=0`은 공용 binary ring 지표이고 `[WINDOW] Dropped windows=295`는 Raw pipeline 지표다. 이름만 보면 서로 모순처럼 보인다.

## 4. 목표 상태

수정 후 다음 불변조건을 만족해야 한다.

1. ACK되지 않은 Raw 원본은 네트워크 상태와 무관하게 durable storage에 남는다.
2. 같은 batch 재시도는 bootId, windowIndex, samples, transmission metadata 및 body hash가 같다.
3. 영구 거부 batch는 짧은 간격으로 무한 재시도하지 않는다.
4. priority 전송과 서버의 stream order 계약이 명시적으로 호환된다.
5. baseline_missing은 모든 window를 priority로 만들지 않는다.
6. HTTP 202/200에서 전체 ACK 식별자가 일치할 때만 삭제한다.
7. 400/401/403/409에서 미ACK 원본은 삭제하지 않는다.
8. 정상 네트워크와 30초 일시 장애에서 Raw drop이 0이다.
9. reboot 후 동일 식별자와 동일 payload로 복구된다.
10. 로그 한 줄만으로 선택된 모든 index, 재시도 분류, 보존/격리 상태를 알 수 있다.

수정 후보:

- 필요 시 새 작은 pure helper와 해당 test 1개

필수 테스트:

1. pending index `3~16`에서 최신 trigger를 우선 선택해 `7~10`, `11~14`를 ACK한 뒤 `5,6,15,16`을 만들 수 있는 현재 실패를 재현한다.
2. server high-water mark가 14인 상태에서 5 또는 6을 신규 전송하면 sendable이 아님을 검증한다.
3. 비연속 선택 결과가 범위가 아닌 실제 index 목록으로 남는지 검증할 기반을 만든다.

- 테스트를 통과시키기 위한 제품 코드 변경은 아직 하지 않는다.

### FIX-02 — baseline_missing 제한 전송 구현

목적: baseline 미설정 상태가 continuous priority flood가 되지 않게 한다.

수정 후보:

- `include\adaptive_transmission.h`
- `src\adaptive_transmission.cpp`
- `test\test_adaptive_transmission\test_main.cpp`
- 필요 최소 범위의 scheduler 연결부

구현 지침:

1. invalid baseline에서 모든 window를 `Mode::Priority`로 반환하지 않는다.
2. `reason=baseline_missing`은 유지하되 전송 eligibility를 별도 cooldown으로 제한한다.
3. 기본 cooldown은 60초로 두고 `ADAPTIVE_BASELINE_MISSING_INTERVAL_MS` 한 개로 조정 가능하게 한다. 운영 값이 제공되면 그 값을 우선한다.
4. cooldown 중 window는 일반 durable backlog로 보존하고 priority trigger로 취급하지 않는다.
5. 부팅 직후 첫 baseline_missing 진단 batch 1회는 허용한다.
6. retry 중에는 cooldown을 다시 시작하거나 body를 재생성하지 않는다.

필수 테스트:

- invalid config의 연속 100개 window가 모두 priority가 되지 않는다.
- 첫 batch 이후 60초 전에는 새 baseline_missing batch가 eligible하지 않다.
- 60초 후에는 1개 batch만 eligible하다.
- quality invalid는 baseline_missing cooldown과 무관하게 즉시 priority다.

완료 조건:

- baseline_missing 상태에서 3분 동안 최대 4회의 신규 진단 batch만 생성된다. 재시도는 신규 batch 수에 포함하지 않는다.

### FIX-03 — 서버 순서 계약 결정 게이트

목적: 서로 동시에 만족할 수 없는 현재 요구를 코드로 숨기지 않는다.

권고안 A — 서버가 out-of-order 신규 window를 허용:

1. 같은 `(deviceId, bootId, windowIndex)`와 같은 digest 재전송은 200 duplicate ACK를 유지한다.
2. 같은 identity의 다른 digest는 계속 409다.
3. 아직 저장되지 않은 낮은 index는 high-water mark보다 낮아도 수락한다.
4. stream high-water mark는 낮아지지 않는다.
5. 누락 구간은 received identity 집합으로 관리하며 늦게 도착한 window로 gap을 메울 수 있게 한다.
6. batch는 계속 원자적으로 처리한다.
7. priority와 transmission metadata 계약 테스트를 추가한다.

대안 B — firmware-only 단조 전송:

1. 같은 boot에서는 가장 낮은 durable 미ACK index보다 높은 index를 먼저 보내지 않는다.
2. priority 표시는 유지하되 실제 전송은 monotonic frontier가 도달할 때까지 기다린다.
3. 이 대안은 원 지침의 `priority가 오래된 periodic backlog보다 먼저 전송` 완료 조건을 만족하지 못한다고 보고한다.

게이트 규칙:

- 전체 정책을 만족하려면 권고안 A가 필요하다.
- backend 변경 권한이 없으면 agent는 대안 B까지만 구현하고 FIX-03을 `부분 완료/정책 불일치`로 보고한다.
- agent가 임의로 이전 미ACK 파일을 삭제하거나 bootId를 바꾸어 우회하면 실패다.

필수 계약 테스트:

- `7~10`, `11~14`를 먼저 수락한 뒤 `5,6`을 보내도 권고안 A에서는 202가 된다.
- 같은 5,6을 다시 보내면 200 duplicate ACK다.
- 같은 identity의 samples 변경은 409다.
- 대안 B에서는 5,6이 남아 있는 동안 7 이상을 선택하지 않는다.

### FIX-04 — 모든 Raw window를 선택 전에 영속 저장

목적: TLS 지연과 재부팅이 capture 유실로 이어지지 않게 한다.

수정 후보:

- `include\continuous_vibration_runtime.h`
- Raw durable record 형식 파일
- 저장 전용 test

구현 지침:

1. processing 완료 후 RAM pending에 넣기 전에 Raw record를 durable storage에 저장한다.
2. network task는 RAM queue가 아니라 durable queue의 index/priority 상태를 선택의 기준으로 사용한다.
3. 한 record에 원본 samples, bootId, windowIndex, startUs, quality, mode, reason, CRC, 상태를 저장한다.
4. 상태는 최소 `ready`, `in_flight`, `quarantined`를 구분한다. 상태 변경은 전원 차단에 안전해야 한다.
5. ACK 전체 일치 후에만 해당 record를 제거한다.
6. `RawSpoolSlots=16` 고정 배열을 5분 정책 완료로 간주하지 않는다.
7. 저장 실패 시 overwrite나 포맷 없이 drop counter와 원인을 남긴다.
8. 수집 task는 LittleFS와 TLS를 직접 호출하지 않는다. 저장 소유권은 한 task로 직렬화한다.
9. 기존 v2 spool은 읽기 호환 또는 명시적 보존 상태로 남기고 자동 삭제하지 않는다.

용량 게이트:

- 실장비 LittleFS 총 2,752,512 bytes, 관측 사용 1,224,704 bytes, 당시 여유 약 1,515,520 bytes였다.
- 기존 공용 binary ring과 Raw storage가 같은 LittleFS를 사용하므로 단순 나눗셈만으로 469개 보존을 보장하면 안 된다.
- adaptive 파티션 전에는 실제 469개 생성·reboot·read-back을 통과하지 못하면 완료 처리하지 않는다.

필수 테스트:

- 40초 network stall 중 생성된 모든 window가 durable queue에 남는다.
- 저장 직후 CRC read-back이 실패하면 전송하지 않는다.
- ACK loss 후 reboot해도 동일 body hash로 재전송한다.
- full 상태에서 기존 record hash가 바뀌지 않는다.

### FIX-05 — HTTP 결과 분류와 bounded retry 구현

목적: 영구 오류의 무한 hot loop를 막고 미ACK 데이터를 보존한다.

수정 후보:

- 작은 pure status classifier
- `include\continuous_vibration_runtime.h`
- classifier native test

분류 규칙:

1. `-1`, timeout, 408, 429, 500~599: retryable
2. 200/202 + 전체 strict ACK: accepted
3. 200/202 + ACK 불일치: protocol hold, 삭제 금지
4. 400, 401, 403: configuration/payload hold, 삭제 금지, 낮은 빈도의 재확인만 허용
5. 409 `WINDOW_CONFLICT`: permanent quarantine, 삭제 금지
6. 409 `WINDOW_SEQUENCE_CONFLICT`: ordering quarantine, 삭제 금지, FIX-03 계약에 따라 재선택
7. 알 수 없는 status: 보존 후 bounded backoff

backoff 지침:

- retryable transport는 2초에서 시작해 4, 8, 16, 최대 30초로 제한한다.
- 성공 ACK 후 해당 endpoint backoff를 초기화한다.
- 409 같은 permanent 결과를 500ms마다 재시도하지 않는다.
- backoff 중에도 capture와 durable 저장은 계속돼야 한다.
- active batch body는 재시도 사이에 재생성하지 않는다.

완료 조건:

- 같은 409 batch의 POST가 3분 동안 수백 회 발생하지 않는다.
- retryable `-1` 뒤 202가 오면 같은 body hash로 성공하고 삭제한다.
- permanent hold/quarantine record는 reboot 후에도 남는다.

### FIX-06 — LittleFS 존재 검사와 파일 lifecycle 정리

목적: 정상적인 빈 slot 탐색이 오류 로그로 보이지 않게 하고 실제 write 실패만 명확히 보고한다.

구현 지침:

1. `LittleFS.exists()` 반복 scan이 VFS error를 발생시키는지 최소 재현으로 확인한다.
2. 확인되면 한 번의 directory scan 또는 오류를 출력하지 않는 존재 검사 방식으로 교체한다.
3. temp write → flush/close → rename → read-back CRC 순서는 유지한다.
4. temp 파일이 남아 있으면 부팅 복구 정책을 명시하고 원본을 자동 덮어쓰지 않는다.
5. 로그를 다음처럼 구분한다.
   - `SPOOL-MISS`: 정상 빈 slot, 기본 로그 생략
   - `SPOOL-WRITE-FAIL`: 실제 write/rename 실패
   - `SPOOL-VERIFY-FAIL`: read-back/CRC 실패

완료 조건:

- 정상 저장 100회에서 `no permits for creation`이 출력되지 않는다.
- write/rename/CRC 실패 주입 테스트는 각각 다른 오류로 남는다.

### FIX-07 — 진단 로그 정확성 수정

목적: 다음 실장비 시험에서 한 번에 원인을 판별한다.

필수 변경:

1. `TX-SELECT`에 실제 index 목록을 출력한다. 예: `indexes=5,6,15,16`.
2. 서로 다른 bootId가 한 batch에 들어가지 않도록 검증하고 bootId 목록 또는 단일 bootId를 출력한다.
3. `STORE-DELETE remaining`은 삭제 후 실제 durable ready/in-flight/quarantine 수를 다시 읽어 출력한다.
4. `raw_attempt`를 실제 attempt 번호로 출력한다.
5. HTTP `-1`에서 가능한 경우 `WiFiClientSecure`의 underlying TLS error code와 문자열을 함께 출력한다.
6. `rawDropped`, `telemetryRingDropped`, `spoolUsed`, `spoolCapacity`, `quarantined`를 다른 이름으로 출력한다.
7. 동일 409 본문은 최초 1회와 상태 변경 시에만 출력한다.

완료 조건:

- 비연속 batch, transport failure, ACK 성공, quarantine을 각각 로그만으로 재구성할 수 있다.

### FIX-08 — 저장 압력과 adaptive N8 파티션 게이트

목적: 5분 469개와 장애 여유를 실제로 확보한다.

선행조건:

- FIX-04 durable queue 완료
- 사용자 또는 담당자의 OTA 슬롯 유지/제거 결정
- 기존 LittleFS backup, SHA-256, restore 절차 준비

구현 지침:

1. 원 지침의 별도 adaptive N8 environment를 사용한다.
2. OTA 결정 전 현재 default environment를 바꾸지 않는다.
3. 파티션 CSV overlap, 8MiB 경계, app 여유, LittleFS 크기를 산술 검증한다.
4. record 실제 byte 수와 실제 생성 가능한 slot 수를 빌드/실장비에서 기록한다.
5. 자동 포맷 플래그를 사용하지 않는다.

완료 조건:

- 469개 이상 저장 후 reboot/mount/read-back 성공.
- 저장 압력 threshold에서 `mode=periodic`, `reason=storage_pressure`가 선택된다.

## 7. 에이전트가 하지 말아야 할 임시 처방

1. RAM queue 크기만 늘려 완료 처리하지 않는다.
2. 409 record를 ACK 없이 삭제하지 않는다.
3. priority마다 bootId를 새로 만들어 서버 순서를 우회하지 않는다.
4. retry 때 JSON body나 droppedWindows를 다시 생성하지 않는다.
5. LittleFS 오류를 포맷으로 해결하지 않는다.
6. 서버 계약 확인 없이 409를 성공으로 취급하지 않는다.
7. 공용 binary ring 24,999 슬롯을 Raw spool 용량으로 보고하지 않는다.
8. `TX-SELECT first-last` 범위 로그만으로 연속 batch라고 판정하지 않는다.
9. TLS `-1`을 인증서 문제로 단정하지 않는다. underlying error를 먼저 수집한다.

## 8. 최종 판정

이번 업로드 자체는 성공했지만 runtime rollout은 실패다. 직접적인 장애 사슬은 다음과 같다.

`baseline_missing 연속 priority` → `낮은 backlog를 건너뛴 높은 index ACK` → `뒤늦은 낮은 index가 서버 409` → `500ms급 영구 재시도` → `pending/rawHold/rawQueue 포화` → `Raw window drop 증가`

초기 TLS `-1`은 이 사슬을 더 빨리 시작하게 한 기여 요인이지만 정확한 TLS 원인은 추가 진단이 필요하다. 근본 해결은 queue 확대가 아니라 서버 순서 계약 정합성, 제한된 baseline_missing 정책, 선택 전 durable 저장, 오류 유형별 재시도 제어를 함께 적용하는 것이다.
