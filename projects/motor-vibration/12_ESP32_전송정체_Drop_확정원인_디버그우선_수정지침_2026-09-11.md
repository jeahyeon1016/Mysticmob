## 00. 이번 단계 결론과 종료선

### 00-01. 현재 수정 방향 판정

1. **안전성 방향은 좋아졌다.** free 4,096 bytes 상태에서 새 spool write를 `LittleFS.open(..., "w")` 전에 차단했고, 최신 3분 동안 divide-by-zero·panic·watchdog·reboot가 없었다.
2. **전송·손실 해결은 아직 완료되지 않았다.** 기존 spool backlog가 전송되는 장면이 없었고 RAM queue는 포화됐다.
3. 현재 상태를 한 줄로 판정하면 **`안전성 개선 O / 전송 진행성 X / TLS 판정 불가`**다.
4. 다음 수정은 저장 구조 확대나 TLS 설정 변경이 아니라, **후보 선택이 어디서 얼마나 오래 막히는지 증명하는 것**부터 시작한다.

### 00-02. 이번 단계에서 허용하는 범위

1. Agent 1은 scheduler·spool selector·Drop 계측과 그에 필요한 최소 테스트만 담당한다.
2. Agent 2는 기존 HTTP/TLS 진단의 상관관계 검토와, 실제 HTTP 진입 후 필요한 최소 로그만 담당한다.
3. Coordinator만 두 결과를 통합하고 build/test·업로드·로그 판정을 수행한다.
4. 첫 실행은 **진단 빌드 1회와 증거 수집까지만** 한다. 원인이 증명되지 않은 동작 변경을 같은 실행에 섞지 않는다.
5. 아래 `08. 판정표`의 조건이 충족된 항목만 다음 실행에서 수정한다.

### 00-03. 금지 사항

1. LittleFS format, 전체 erase, partition 변경, 기존 record 삭제를 하지 않는다.
2. queue/ring 크기 증가, timeout/retry 증가, 임의 reserve 값 조정을 해결책으로 사용하지 않는다.
3. 5분 정책을 3분 시험에 맞추기 위해 즉시 축소하지 않는다.
4. 과거 boot record를 timestamp 근거 없이 즉시 전송하지 않는다.
5. TLS CA, URL, 인증, connection reuse 동작은 HTTP 진입 증거 전에는 변경하지 않는다.
6. `MotorDiagnosis` commit/push/PR은 하지 않는다.
7. token, 인증서 본문, Wi-Fi 비밀번호, 전체 URL을 로그에 출력하지 않는다.

## 01. 최신 상태에서 확인된 사실

### 01-01. 안전 gate 결과

1. LittleFS: total 2,752,512 / used 2,748,416 / free 4,096 bytes.
2. boot admission: `suspended=yes`, 이유 `observed_unsafe_state`.
3. boot cursor scan: 350개 검사, next slot 349, 약 7.19초.
4. 새 spool write는 open 전에 fail-closed 됐고 storage timing sample은 0이었다.
5. 최신 3분 동안 panic·watchdog·reboot·TLS `-1`은 관찰되지 않았다.

### 01-02. 실패 결과

1. 기존 binary ring backlog 2,747개가 복원됐다.
2. `pending=8`, `raw_queue=8`로 포화됐다.
3. `capture_queue_full`, `processing_pending_full`, `spool_capacity_full`이 증가했다.

5. 따라서 TLS `-1` 미발생은 TLS 개선 증거가 아니다. HTTP 경로가 충분히 실행되지 않았기 때문이다.

## 02. 코드와 로그로 확정된 문제

### 02-01. 3분 관찰과 5분 periodic cutoff의 불일치

확정 근거:

1. `PeriodicScheduler::CutoffUs`는 `300,000,000 us`, 즉 5분이다.
2. 부팅 후 5분 이내에는 `cutoff(nowUs)`가 0이다.
3. priority가 아닌 spool/pending record는 `startUs <= cutoffUs`일 때만 선택된다.
4. 정상 window의 `startUs`는 0보다 크므로 3분 관찰 중 일반 periodic 후보는 선택되지 않는다.
5. native test도 “5분 전에는 선택 0개”를 현재 정책으로 고정한다.

판정:

- 3분 로그만으로 일반 periodic 전송 성공 여부를 판정한 기존 시험은 정책과 맞지 않는다.
- 이것만으로 5분 정책이 잘못됐다고 단정하지 않는다. 시험 시작 조건을 고치거나, 정책 자체를 별도 승인받아야 한다.

### 02-02. fail-closed 상태에서는 새 RAM batch가 HTTP까지 진행할 수 없음

확정 근거:

1. pending batch를 선택해도 HTTP 전에 모든 window를 `writeRawSpool()`로 영속화한다.
2. `rawSpoolWritesSuspended=true`이면 `writeRawSpool()`은 즉시 false를 반환한다.
3. 그러면 network task는 batch를 비우고 `pre-send persistence failed`로 전송을 연기한다.

판정:

- 현재 fail-closed는 panic 방지에는 맞지만, **새 데이터의 전송 우회로가 아니다**.
- durable-before-send 정책을 유지하는 한 저장 중단 상태의 새 RAM 데이터는 전송하지 않는 것이 현재 코드의 정확한 동작이다.
- 이 정책을 임의로 깨서 비영속 전송으로 바꾸지 않는다.

### 02-03. RAM 수용량보다 첫 전송 가능 시점이 훨씬 늦음

확정 근거:

1. window 주기는 약 0.64초다.
2. `pending=8`과 `raw_queue=8`은 합계 약 10.24초 분량이다.
3. 새 spool write가 중단됐고 일반 periodic 선택은 5분 전까지 불가능하다.
4. 초기 priority 1건 외 대부분은 periodic으로 분류될 수 있다.

판정:

- 현재 조건에서는 정상 생산이 계속되는 동안 5분보다 훨씬 전에 queue 포화와 실제 capture drop이 발생한다.
- queue를 키우는 것은 5분과 저장 중단 문제를 가릴 뿐 근본 해결이 아니다.

### 02-04. 과거 boot의 `startUs`를 현재 boot cutoff와 비교하는 것은 잘못됨

확정 근거:

1. raw spool header에는 record의 `bootId`와 `startUs`가 저장된다.
2. `startUs`는 해당 boot 기준의 monotonic uptime이다.
3. `loadRawSpoolBatch()`는 record의 `bootId`를 현재 boot와 비교하지 않고 `header.startUs > cutoffUs`만 검사한다.
4. `cutoffUs`는 현재 boot의 uptime에서 계산된다.

판정:

- 서로 다른 boot의 monotonic 시간을 같은 시간축처럼 비교하는 것은 확정된 시간 도메인 오류다.
- 다만 “과거 boot면 즉시 eligible”만 적용하면 timestamp 문제가 남으므로 바로 수정하지 않는다.

### 02-05. 과거 boot raw record의 정확한 timestamp 복원 근거가 부족함

확정 근거:

1. 전송 JSON의 timestamp는 `timestamp(f.startUs, epochOffset)`으로 만든다.
2. `epochOffset`은 현재 boot의 UTC와 현재 boot uptime으로 생성된다.
3. raw spool record는 과거 `bootId`와 `startUs`를 보유하지만, 그 boot의 epoch offset 또는 직접적인 capture epoch를 보유하지 않는다.
4. boot ID는 시작 시 난수로 생성되며 현재 코드에서 과거 UTC anchor와의 명시적 mapping이 확인되지 않았다.

판정:

- 과거 record에 현재 boot의 epoch offset을 적용하면 정확한 capture timestamp라고 보장할 수 없다.
- 기존 record를 삭제하거나 timestamp를 추정해서 보내지 않는다.
- 먼저 서버 계약상 timestamp 정확도와 기존 anchor mapping 가능 여부를 증명해야 한다.

### 02-06. `processing_pending_full`은 고유 drop 수가 아님

확정 근거:

1. 같은 held raw가 pending full 상태에서 재시도될 때마다 counter가 증가하는 경로가 있다.
2. 최신 로그에서는 실제 capture 수보다 훨씬 빠르게 수천 단위로 증가했다.
3. `raw_hold_full=0`인 동안 pending full이 발생해도 해당 raw의 소유권이 즉시 유실된 것은 아니다.
4. 반면 `capture_queue_full`은 `xQueueSend(..., 0)` 실패 시 실제 capture window가 queue에 들어가지 못한 직접 손실이다.

판정:

- `processing_pending_full`은 압력/재시도 event 수다.
- 현재 이름만 보고 전체를 `Dropped windows`로 합산하면 손실량을 과대평가할 수 있다.

## 03. 아직 확정하지 말아야 할 부분

### 03-01. selector scan이 network 정체의 실제 주원인인지

확인된 코드 특성:

1. `loadRawSpoolBatch()`는 최대 batch 4개를 채우는 동안 최대 512 slot을 반복 순회한다.
2. 각 존재 slot에 stat과 header open/read/close가 수행된다.
3. boot 시 단순 slot scan도 약 7.19초가 걸렸다.

미확정 사항:

- network task의 실제 selector 총시간, lock wait, stat/header read 비중은 아직 측정되지 않았다.
- 따라서 selector가 느릴 가능성은 높지만, 이번 3분 정체의 단독 원인으로 확정하지 않는다.

### 03-02. 안전한 LittleFS reserve 값

- free 4,096 bytes 상태가 위험했다는 관찰은 있다.
- allocator에 필요한 정확한 여유량과 자동 해제 기준은 증명되지 않았다.
- 현재 4,096 기준은 안전 진단 latch로 유지하며 숫자를 조정하지 않는다.

### 03-03. TLS `-1` 원인

- 과거 로그에서 status `-1`과 202 성공이 모두 있었다.
- 최신 로그는 HTTP attempt 자체가 충분하지 않았다.
- selector가 HTTP까지 도달한 뒤에만 DNS/TLS/HTTP event ID를 이용해 판정한다.

## 04. Agent 1 작업 — scheduler·spool selector·Drop

### A1-12-01. 기준선 고정

1. 다음 항목의 현재 값과 소스 위치를 보고한다.

2. 현재 native test 결과와 N8 build 결과를 기록한다.
3. 이 단계에서는 동작을 변경하지 않는다.

### A1-12-02. selector 요약 계측 추가

목적: slot별 로그를 찍지 않고 selector 한 번의 비용과 탈락 이유를 측정한다.

필수 필드:

1. `event`, `mode=priority|periodic`
2. `now_us`, `cutoff_us`, `elapsed_us`
3. `slots_checked`, `headers_present`, `header_read_fail`
4. `eligible`, `selected`, `cutoff_rejected`
5. `current_boot_records`, `restored_boot_records`
6. `stat_total_us`, `stat_max_us`, `header_total_us`, `header_max_us`
7. `payload_total_us`, `lock_wait_us`

구현 지침:

```cpp
// 예시 형식. 기존 함수에 지역 counter만 추가하고 새 logging framework는 만들지 않는다.
Serial.printf(
    "[RAW-SELECT-DIAG] event=%lu mode=%s now_us=%llu cutoff_us=%llu "
    "slots=%u present=%u read_fail=%u eligible=%u selected=%u rejected=%u "
    "current_boot=%u restored_boot=%u stat_total_us=%lu stat_max_us=%lu "
    "header_total_us=%lu header_max_us=%lu payload_total_us=%lu "
    "lock_wait_us=%lu elapsed_us=%lu\n",
    /* measured values */);
```

제약:

1. slot마다 출력하지 않고 selector 호출당 begin/end 요약 1세트만 출력한다.
2. boot ID 전체를 출력하지 않는다. current/restored 분류와 개수만 출력한다.
3. counter 계산 때문에 추가 filesystem scan을 만들지 않는다.
4. 선택 조건과 반환값은 변경하지 않는다.

### A1-12-03. network 진행 단계 계측 추가

아래 단계에 동일 event ID를 사용한다.

1. `loop_ready`
2. `time_ready`
3. `priority_scan_begin/end`
4. `periodic_scan_begin/end`
5. `pending_select`
6. `payload_ready`
7. `pre_send_persist_begin/end`
8. `http_begin`

최소 예시:

```cpp
Serial.printf("[RAW-TX-STAGE] event=%lu stage=%s elapsed_us=%lu size=%u\n",
              eventId, stage, elapsedUs, size);
```

제약:

- 1회 network loop마다 무제한 출력하지 않는다. batch 선택 시도 또는 장시간 selector 호출에만 출력한다.
- URL, token, 인증서 내용은 출력하지 않는다.

### A1-12-04. Drop counter 의미 분리

1. 기존 counter를 제거해 호환성을 깨지 않는다.
2. 로그에서 `processing_pending_full`을 `processing_pending_full_events`로 명확히 표시한다.
3. 같은 `{bootId, windowIndex}`의 반복 retry와 최초 pressure를 구분하는 `processing_pending_full_unique`를 최소 상태로 추가한다.
4. `actual_drop_total`은 소유권이 실제로 사라지는 경로에서만 증가하도록 정의한다.
   - capture queue enqueue 실패
   - pending과 raw hold 모두 수용 실패
   - 그 밖의 실제 폐기 경로가 소스에서 확인된 경우
5. 같은 raw의 재시도는 unique 또는 actual drop을 반복 증가시키지 않는다.

최소 테스트:

1. 같은 window의 pending-full 3회: events 3, unique 1, actual drop 0.
2. capture enqueue 실패 1회: actual drop 1.
3. raw hold 성공: actual drop 증가 없음.

### A1-12-05. cross-boot 시간 증거 추가

1. selector에서 current/restored boot 후보 수와 cutoff 탈락 수를 수집한다.
2. raw spool header가 가진 시간 필드와 현재 timestamp 생성 입력을 표로 보고한다.
3. 과거 boot ID가 기존 durable time anchor와 연결되는 코드 경로가 있는지 호출자까지 추적한다.
4. 연결 경로가 없으면 **`timestamp reconstruction unproven`**으로 보고하고 동작 변경을 중단한다.
5. 이 단계에서 과거 record의 eligibility를 변경하거나 임의 timestamp를 생성하지 않는다.

2. Agent 2가 scheduler/storage 동작을 바꾸지 않았는지 확인한다.
3. selector 조건, 5분 cutoff, durable-before-send, reserve 값이 그대로인지 diff로 확인한다.
4. 새 추상화·새 dependency·slot별 로그가 추가되지 않았는지 확인한다.
5. 실제 drop과 pressure event가 중복 집계되지 않는지 테스트와 증가 지점을 대조한다.

### C-12-03. 로컬 검증

순서:

1. 관련 native test
2. 전체 `pio test -e native`
3. `pio run -e esp32-s3-devkitc-1-n8`
4. 대상 파일 `git diff --check`
5. ELF SHA256 기록

하나라도 실패하면 업로드하지 않고 실패 번호와 첫 오류를 보고한다.

## 07. 업로드와 로그 시험

### C-12-04. 업로드 조건

1. C-12-03이 모두 통과해야 한다.
2. firmware만 COM7에 업로드한다.
3. filesystem image, format, erase, partition upload를 실행하지 않는다.
4. 실제 업로드한 ELF hash를 기록한다.

### C-12-05. 관찰 시간 정의

1. 부팅 직후부터 serial 로그를 수집한다.
2. **유효 3분 관찰은 첫 `[RAW-SELECT-DIAG] ... end` 또는 `[RAW-TX-STAGE] ... stage=http_begin`이 나온 시점부터 계산한다.**
3. 5분 cutoff 때문에 그 전까지 일반 periodic 후보가 없으면, 이를 실패나 TLS 정상으로 오판하지 않는다.
4. 8분 이상 기다려도 selector end 또는 http begin이 한 번도 없으면 `network/selector progress failure`로 중단·보고한다.
5. panic, watchdog, reboot가 발생하면 즉시 시각과 마지막 stage를 보존하고 중단한다.

### C-12-06. 반드시 수집할 값

1. selector 호출별 elapsed와 세부 합계
2. current/restored boot record와 cutoff reject 수
3. selector begin/end 및 HTTP begin 도달 여부
4. `capture_queue_full`
5. `processing_pending_full_events`
6. `processing_pending_full_unique`
7. `actual_drop_total`
8. TLS/HTTP status와 DNS result의 동일 event 상관관계
9. ACK와 spool delete 여부
10. panic/watchdog/reboot 여부

## 08. 증거별 다음 수정 판정표

### D-12-01. selector가 실제 병목으로 확인됨

조건:

- selector `elapsed_us`가 반복해서 window 주기 640,000 us를 넘고, stat/header scan이 대부분을 차지한다.

다음 허용 작업:

1. 기존 boot cursor/index 정보를 재사용해 매 batch의 full scan을 없애는 가장 작은 변경안을 작성한다.
2. 같은 record 선택 순서와 CRC/read-back 규칙을 보존하는 native test를 먼저 만든다.
3. fixed ring 재설계는 이 최소 수정으로 목표를 달성하지 못한 측정값이 있을 때만 별도 계획으로 연다.

### D-12-02. cutoff만 후보를 막고 selector 시간은 짧음

조건:

- selector는 정상 종료하지만 `cutoff_rejected > 0`, `selected=0`이며 현재 boot record만 존재한다.

다음 조치:

1. 이는 현재 5분 정책의 예상 동작이다.
2. 정책을 유지하면 “부팅 후 5분 + 유효 3분” 시험으로 검증한다.
3. 5분 전 전송이 제품 요구라면 별도 정책 변경 승인을 받고 `PeriodicScheduler`와 기존 test를 함께 변경한다.

### D-12-03. restored boot record가 cutoff로 막힘

조건:

- `restored_boot_records > 0`, `cutoff_rejected > 0`, selected 0 또는 과도한 지연.

다음 조치:

1. cross-boot monotonic 비교 오류는 수정 대상이다.
2. 단, A1-12-05에서 과거 timestamp를 정확히 복원할 mapping이 확인된 경우에만 restored record를 현재 boot cutoff와 분리한다.
3. mapping이 없으면 기존 record를 유지하고, spool header에 capture epoch 또는 durable anchor identity를 저장하는 versioned 최소 변경 계획을 별도로 작성한다.
4. 기존 header의 timestamp를 추정하거나 record를 삭제하지 않는다.

### D-12-04. HTTP 진입 후 status `-1` 재현

조건:

- 동일 event에서 `http_begin` 뒤 status `-1`과 DNS/TLS 진단이 수집된다.

다음 조치:

1. DNS 실패이면 DNS/Wi-Fi 경로만 조사한다.
2. DNS 성공인데 connect/TLS 전이면 lower-level error와 heap/socket 상태를 추가로 한 번 계측한다.
3. 202와 `-1`이 혼재하면 영구 CA/URL 오류로 단정하지 않는다.
4. 원인 증거 없이 timeout/retry/CA를 변경하지 않는다.

### D-12-05. actual drop과 pressure event가 다름

조건:

- events는 증가하지만 unique/actual drop이 증가하지 않는다.

다음 조치:

- pressure event를 손실 수로 보고하지 않는다. 실제 drop 경로만 운영 지표로 사용한다.

## 09. 완료 조건

이번 지침은 아래가 모두 충족되면 완료다.

1. 두 Agent 보고 번호가 모두 수신됐다.
2. selector begin/end와 실제 소요 시간이 확인됐다.
3. current/restored/cutoff rejection이 수치로 분리됐다.
4. 실제 drop과 retry pressure event가 분리됐다.
5. HTTP 미진입과 TLS 실패가 구분됐다.
6. native test, N8 build, diff check가 통과했다.
7. firmware-only 업로드 후 유효 3분 로그가 수집됐다.
8. `08. 판정표` 중 정확히 어떤 분기로 들어갔는지 번호로 보고됐다.
9. 원인이 확정되지 않은 영역에 동작 변경을 적용하지 않았다.
